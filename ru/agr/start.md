# 1. Введение: Контекст и задача

**АГР** (Архитектурно-градостроительный облик) — это официальный комплект документов, который проектировщик подаёт в городскую администрацию/экспертизу перед согласованием строительства. Он состоит из двух цифровых файлов:  

1. **Паспорт проекта (XML)** — структурированные текстовые данные: адрес, этажность, площадь, участники проектирования, функциональное назначение.

2. **3D-модель (IFC)** — не просто «картинка», а умная модель, где у каждого **объекта** (стена, окно, этаж) есть **метаданные**: материал, код по классификатору, геометрические параметры, привязка к нормативам.

## Проблема

Городская экспертиза принимает документы **только при строгом соответствии формату**:

- В XML не заполнено поле `BuildingHeight` — отказ.

- В IFC у окна отсутствует свойство `RUS_GlazingArea` — отказ.

- Файл называется не по шаблону — отказ.

## Решение

 Программа позволяет команде проверить документы **до отправки**.

# 2. Базовые понятия: BIM, IFC и PSet

## Что такое BIM?

**BIM** (Building Information Modeling) — это цифровая модель здания, где каждый элемент — это запись в базе данных с типом, свойствами и связями.

## Что такое IFC?

**IFC** (Industry Foundation Classes) — открытый текстовый стандарт обмена BIM-данными (ISO 10303-21, формат STEP). Это универсальный язык, понятный любой программе: Revit, ArchiCAD, NanoCAD, сметным системам.
  

IFC — это не 3D-меш, а **плоский список записей**, связанных по ID:
```
#100 = IFCWALL('GUID_123...', ..., 'Стена наружная', ...);

#200 = IFCPROPERTYSET('GUID_456...', ..., 'RusSet_Common', ..., (#201, #202, #203));

#201 = IFCPROPERTYSINGLEVALUE('RUS_Name', ..., IFCSTRING('Стена несущая'), ...);

#202 = IFCPROPERTYSINGLEVALUE('RUS_MSSK_Element_Code', ..., IFCSTRING('C.01.02.01'), ...);

#300 = IFCRELDEFINESBYPROPERTIES(..., [#100], #200);

```

## Что такое PSet (Property Set)?

**PSet (Property Set)** — это именованный набор свойств (ключ-значение), который хранится отдельно от объекта и подключается к нему через связь.

| Объект в модели | Без PSet             | С PSet `RusSet_Common`                                 |
| --------------- | -------------------- | ------------------------------------------------------ |
| Стена           | Просто геометрия     | + `RUS_Name`, `RUS_MSSK_Element_Code`, `RUS_Thickness` |
| Окно            | Просто прямоугольник | + `RUS_Width`, `RUS_Height`, `RUS_GlazingArea`         |

> **Почему так?** Один объект может использоваться в разных контекстах (смета, энергоаудит, пожарка). Вместо «раздувания» класса свойствами IFC использует внешние наборы (PSet), которые прицепляются по необходимости.

  

## Уровни стандартов в проекте

```

Уровень 1: Международный стандарт (IFC)

    IfcWall, IfcWindow, IfcSpace — типы объектов

    Аналог: базовые классы в ООП

  

Уровень 2: Российская надстройка (требования Москвы/АГР)

    RusSet_Common, RusSet_AGR, RusSet_Quantities — имена PSet

    Аналог: интерфейсы, которые должен реализовать объект

  

Уровень 3: Конкретные поля (данные)

    RUS_Name, RUS_MSSK_Element_Code, RUS_Width

    Аналог: обязательные поля в JSON Schema / Pydantic

```

# 3. Контракт валидации: что именно проверяем

Государство задаёт жёсткий контракт. Программа проверяет его на двух уровнях.

## Для XML (`check-xml`)

- Все обязательные теги присутствуют и не пусты.

- Числовые поля действительно содержат числа.

- Даты в формате `YYYY-MM-DD`.

- `WorkTypes` входит в множество: `{новое строительство, реконструкция, новое строительство и реконструкция}`.

- Контейнеры `<ProjectTeam>`, `<FunctionalPurposes>` содержат вложенные элементы.

## Для IFC (`check-ifc`)

- Имя файла соответствует шаблону: `[prefix_]П1_П2[_П3]_П4_АГР[_version].ifc`.

- У каждого проверяемого типа (`IfcWall`, `IfcWindow` и др.) есть требуемые PSet.

- Внутри каждого PSet заполнены обязательные свойства.

# 4. Архитектура утилиты `xml-agr`

Утилита построена по принципу **разделения ответственности**. Три независимые подкоманды, каждая закрывает свой этап жизненного цикла.

## 4.1 `cli.py` — Маршрутизатор

```python

sub = parser.add_subparsers(dest="command", required=True)

gen_p = sub.add_parser("generate")   # → generator.py

cx_p  = sub.add_parser("check-xml")  # → xml_checker.py

ci_p  = sub.add_parser("check-ifc")  # → ifc_checker.py

```

## 4.2 `generator.py` — Сериализатор DTO

Превращает Python-словарь (из JSON или интерактивного ввода) в валидный XML. 

## 4.3 `xml_checker.py` — Валидатор паспорта

Легковесный валидатор без XSD. Возвращает `CheckResult(type="ok"|"warn"|"err")`.
  
```python

def check_xml(content: str) -> list[CheckResult]:

    root = ET.fromstring(content)

    # 1. Проверка обязательных тегов

    # 2. Проверка типов (float/int)

    # 3. Проверка enum (WorkTypes)

    # 4. Проверка контейнеров и формата даты

```
  
## 4.4 `ifc_checker.py` → `IFC_RULES` — Схема контракта

Декларативная конфигурация. Если требования изменятся, достаточно поправить этот словарь. Никакого хардкода в логике проверки.

```python

IFC_RULES: dict[str, dict[str, list[str]]] = {

    "IfcWall": {

        "RusSet_Common": ["RUS_MSSK_Element_Code", "RUS_Name", "RUS_MSSK_Element_Name"],

        "RusSet_Quantities": ["RUS_Thickness"],

        "RusSet_Location": ["RUS_Object", "RUS_Object_Sub"],

    },

    "IfcWindow": { ... },

}

```
  
## 4.5 `IfcTextParser` — Восстановление графа

1. Индексирует записи `#ID=TYPE(...)` в словарь.

2. Кэширует имена свойств и группирует их в PSet.

3. Восстанавливает связи «Элемент → PSet» через `IFCRELDEFINESBYPROPERTIES`.

```python

class IfcTextParser:

    def __init__(self, text: str) -> None:

        self._line_map = {}             # #ID → строка

        self.psets = {}                 # #ID → (имя_PSet, {имена_свойств})

        self.element_pset_names = {}    # #ID_элемента → {имя_PSet: {имена_свойств}}

        self._parse(text)

        self._build_psets()

        self._build_element_psets()

```

## 4.6 `check_ifc_file` — Rule-Engine

Линейный валидатор. Не чинит модель, только сообщает, чего не хватает. GUID в отчёте позволяет мгновенно найти проблемный элемент в BIM-редакторе.

```python
def check_ifc_file(path: Path) -> list[IfcIssue]:

    parser = IfcTextParser(text)

    elements = parser.iter_category_elements()

  

    for el_id, category, el_psets in elements:

        required_psets = IFC_RULES[category]

        for pset_name, required_props in required_psets.items():

            if pset_name not in el_psets:

                issues.append(IfcIssue(..., f"Отсутствует группа параметров: {pset_name}", "warn"))

                continue

            existing = el_psets[pset_name]

            for prop in required_props:

                if prop not in existing:

                    issues.append(IfcIssue(..., f"Параметр не найден: {pset_name} → {prop}", "err"))

    return issues
```
  
### 4.7 `check_ifc_filename` — Валидатор naming convention

Парсит имя по `_`, проверяет каждую часть регулярками. Государство требует строгий шаблон для автоматической маршрутизации файлов в приёмной системе.

```

Формат: [prefix_]П1_П2[_П3]_П4_АГР[_version].ifc

П1: НН/ПН, П2: К01/ОБ01, П3: С01, П4: АР/ПС, П5: АГР

```

# 5. Примеры валидации в действии

## XML: валидный фрагмент vs ошибка  

```xml

<FloorsCount>25</FloorsCount>              <!-- OK -->

<FloorsCount>двадцать пять</FloorsCount>   <!-- Ошибка типа: ожидалось число -->

```


## IFC: абстрактный фрагмент (стена)

| Строка                                                           | Что это             | Аналогия в БД                             |
| ---------------------------------------------------------------- | ------------------- | ----------------------------------------- |
| `#100 = IFCWALL(...)`                                            | Объект «Стена»      | `elements.id = 100`                       |
| `#200 = IFCPROPERTYSET(..., 'RusSet_Common', ..., (#201, #202))` | Набор свойств       | `property_sets.id = 200`                  |
| `#201 = IFCPROPERTYSINGLEVALUE('RUS_Name', ...)`                 | Конкретное свойство | `properties.key = 'RUS_Name'`             |
| `#300 = IFCRELDEFINESBYPROPERTIES(..., [#100], #200)`            | Связь               | `element_pset_rel(element=100, pset=200)` |

  

## Имя файла: корректные и некорректные имена

| Имя файла                    | Статус         | Почему                             |
| ---------------------------- | -------------- | ---------------------------------- |
| `НН_К01_АР_АГР.ifc`          | OK             | НН, К01, АР, АГР                   |
| `ПН_ОБ02_ПС_АГР_v2.ifc`      | OK             | ПН, ОБ02, ПС, версия 2             |
| `model_final.ifc`            | Ошибка         | Нет шифров, нет «АГР»              |
| `НН_К01_АР_АГР_черновик.ifc` | Предупреждение | После «АГР» допустимы только цифры |

# 6. Жизненный цикл процесса

```

1. Проектировщик экспортирует из BIM

   - agr_tep.xml

   - model_АР.ifc

  

2. Запускает утилиту:

   $ xml-agr check-xml agr_tep.xml

   $ xml-agr check-ifc model_АР.ifc

  

3. Получает отчёт:

   OK   XML: все поля заполнены

   WARN IFC: у 3 окон нет RUS_GlazingArea

   ERR  Имя файла: должно быть НН_К01_...

  

4. Исправляет ошибки в BIM-редакторе,

   переэкспортирует и проверяет снова.

  

5. Когда всё зелёное — отправка в госэкспертизу.

```
